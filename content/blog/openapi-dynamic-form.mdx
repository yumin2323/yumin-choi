Yetter는 노드를 이어 이미지와 비디오를 생성하는 AI 서비스입니다. 사용자는 모델을 고르고, 모델마다 다른 입력값을 채워 실행합니다.

## 문제

모델마다 받는 입력이 다릅니다. 프롬프트 하나만 받는 모델도 있고, 이미지와 여러 개의 수치 옵션, 중첩된 설정 객체를 함께 받는 모델도 있습니다.

처음에는 모델이 추가될 때마다 입력 폼을 직접 만들었습니다. 모델 하나에 **2~3시간의 프론트엔드 작업**이 필요했고, 모델 추가 속도가 곧 프론트엔드 작업 속도에 묶여 있었습니다.

## 이미 있는 정보를 쓰기

모델 API는 이미 OpenAPI 스키마로 입력 형식을 설명하고 있었습니다. 어떤 필드가 있는지, 타입은 무엇인지, 필수 여부와 기본값, 허용 범위까지 들어 있었습니다. 화면이 필요로 하는 정보는 대부분 그 안에 있었습니다.

그래서 폼을 손으로 만드는 대신 **스키마를 해석해 폼을 구성**하기로 했습니다.

## 구조

스키마의 각 필드를 타입에 따라 알맞은 입력 컴포넌트로 연결하는 것이 핵심입니다. 아래는 개념을 단순화한 예시입니다.

```tsx
function Field({ name, schema }: { name: string; schema: SchemaObject }) {
  if (schema.enum) return <Select name={name} options={schema.enum} />;

  switch (schema.type) {
    case "string":
      return <TextInput name={name} />;
    case "number":
    case "integer":
      return <NumberInput name={name} min={schema.minimum} max={schema.maximum} />;
    case "boolean":
      return <Switch name={name} />;
    case "object":
      // 중첩 객체는 같은 규칙으로 다시 그린다
      return <FieldGroup name={name} properties={schema.properties} />;
  }
}
```

중첩된 객체와 배열도 같은 규칙을 재귀적으로 적용해, 폼 상태 역시 스키마와 같은 모양의 데이터로 만들어지도록 했습니다. 덕분에 입력값을 API 요청으로 바꿀 때 따로 변환할 일이 거의 없었습니다.

## 결과

이제 새 모델이 추가되어도 **코드 수정 없이 입력 화면이 바로 만들어집니다.** 모델 하나마다 들던 2~3시간의 작업이 사라졌고, 모델 추가는 프론트엔드 일정과 관계없이 진행할 수 있게 됐습니다.

## 돌아보며

같은 작업이 반복된다면, 그 작업에 필요한 정보가 이미 어딘가에 있는지 먼저 살펴봅니다. 이번에는 API 스키마가 그 답이었습니다.
